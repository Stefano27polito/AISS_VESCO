\section{Verifiable Credentials (VC)}

Verifiable Credentials (VCs) represent the third layer of the self-sovereign identity framework. 
\medskip

\noindent
VCs are digital credentials, conceptually similar to physical documents such as identity cards or driving licences, but expressed using a structured JSON-based data model. They are designed to support lifelong, secure, and rich identity descriptions, in line with the requirements defined for SSI systems.
\medskip

\noindent
The data model for verifiable credentials is defined by the W3C Verifiable Credentials Working Group and is currently specified in version-2.0. As with the DID specification, the model is extensible and supports custom vocabularies and domain-specific attributes.
\medskip

\noindent
A credential becomes “verifiable” because it is digitally signed by the issuer. This ensures authenticity, integrity, and resistance to tampering. Holders can generate a verifiable presentation by packaging one or more credentials and signing the presentation themselves. 
This presentation can then be shared with a verifier following either a two-party or three-party interaction model.

\subsection {Three- and Two-Party Interaction Models}

The most common interaction pattern for verifiable credentials is the 
\textbf{three-party model}, involving:
\begin{itemize}
    \item \textbf{Issuer}: creates and signs the verifiable credential.
    \item \textbf{Holder}: stores one or more credentials and generates 
    verifiable presentations by signing them.
    \item \textbf{Verifier}: receives the presentation and validates its 
    authenticity, integrity, and structure.
\end{itemize}

\noindent
The verifier performs several checks:
\begin{itemize}
    \item verifies the holder’s signature on the verifiable presentation,
    \item verifies the issuer’s signature on each embedded credential,
    \item validates the credential schema (typically published by the issuer on a VDR),
    \item relies on \textit{implicit trust} in the issuer, since no direct 
    interaction occurs between verifier and issuer during verification.
\end{itemize}

\noindent
This model reflects the SSI principle of peer-to-peer interactions: holders interact directly with issuers when obtaining credentials and with verifiers when proving their identity. \\
Verifiable credentials therefore contain the holder’s DID, which binds the credential to the subject and allows the verifier to retrieve the public key associated with the DID.
\medskip

\noindent
Although outside the scope of this module, verifiable credentials may also be combined with zero-knowledge proofs, enabling holders to prove certain properties without revealing all credential attributes.
\medskip

\noindent
A less common alternative is the \textbf{two-party model}, where issuer and verifier coincide. \\
The holder presents the credential back to the same entity that issued it. This model is used in niche scenarios, for example when credentials are employed to regulate access frequency or service usage.\\
However, the three-party model remains the standard for most SSI deployments.

\subsection {Verifiable Data Registry (VDR)}

At the core of the verifiable credential ecosystem lies the 
\textbf{Verifiable Data Registry (VDR)}, which maintains the identifiers 
(e.g., DIDs) and the credential schemas required for interoperability.  
Even if a verifier trusts a specific issuer, it must still retrieve the 
schema of the credential in order to correctly interpret and validate the 
claims. For this reason, issuers typically publish credential schemas on 
the VDR.
\medskip

\noindent
In addition to identifiers and schemas, the VDR may also maintain 
\textbf{revocation information}, enabling verifiers to check whether a 
credential is still valid. Although not shown in all conceptual diagrams, 
revocation is an essential component of the full lifecycle of VCs.

\paragraph{Issuer.}
The issuer creates and signs verifiable credentials. Before issuing a 
credential, it verifies the holder’s identifier (e.g., the DID) by 
confirming control of the associated private key. Issuers also interact 
with the VDR to retrieve or publish credential schemas.

\paragraph{Holder.}
The holder acquires, stores, and presents verifiable credentials using a 
dedicated \textit{wallet}. The holder assembles verifiable presentations 
by wrapping credentials and signing the presentation with their own private 
key. The holder may also query the VDR to verify identifiers or schemas.

\paragraph{Verifier.}
The verifier validates incoming verifiable presentations by checking the 
holder’s signature, the issuer’s signature on each credential, schema 
 correctness, and—when applicable—revocation status.  
To perform these checks, the verifier queries the VDR for identifiers, 
schemas, and auxiliary validation data.

\subsection {Verifiable Credential Structure}

A verifiable credential contains a structured set of information describing the subject.\\
The VC data model defines a minimal mandatory structure while allowing extensibility so that issuers may include additional attributes when needed.\\ 
The most relevant components are the following:

\paragraph{Subject Information.}
The credential contains claims about the subject. \\ 
These claims represent identity attributes or properties (e.g., name, role, device characteristics) and are expressed in a structured JSON object. \\
One essential element is the subject’s \textbf{DID}, which links the credential to the subject’s decentralized identifier.

\paragraph{Issuer Information.}
Each credential specifies the \textbf{issuer}, identified by a DID.\\  
This allows a verifier to locate the issuer’s public key and to validate the issuer’s signature during the verification process.

\paragraph{Credential Type.}
VCs indicate their type, which may represent generic classes (e.g., 
\texttt{VerifiableCredential}) or domain-specific credentials such as a university degree or a device-attestation credential. \\ 
Types enable verifiers to interpret the structure and semantics of the claims.

\paragraph{Claims and Assertions.}
The issuer is responsible for determining the truthfulness of all claims before including them in the credential. \\ 
In many human-oriented scenarios, this implies verifying attributes through real-world processes (e.g., checking a physical ID document). \\ 
In automated or IoT settings, claims may instead be verified digitally within a controlled environment.

\paragraph{Credential Constraints.}
A credential may include additional metadata such as usage constraints, validity periods, or purpose-specific fields. \\ 
These help verifiers correctly interpret the credential and determine whether it is acceptable in their context.

\paragraph{Proof.}
Each verifiable credential contains a cryptographic \textbf{proof} section, normally a digital signature produced by the issuer. \\ 
This proof ensures authenticity, integrity, and tamper-evidence of the credential.

\medskip

\noindent
A verifiable credential can therefore be understood as a structured combination of:
\begin{itemize}
    \item metadata,
    \item claims describing the subject,
    \item and a cryptographic proof from the issuer.
\end{itemize}
Together, these elements allow the credential to be validated by any verifier that trusts the issuer and can interpret the associated schema.
\subsection{VC Components}

\subsubsection*{Subject and Claims}

A claim is a statement about a subject.  
Claims follow a \textbf{subject–property–value} structure, allowing the issuer
to describe specific attributes of the credential subject.  
Compared to DID, verifiable credentials allow richer and more expressive
descriptions, enabling issuers to represent detailed identity information.

\begin{verbatim}
{
  "credentialSubject": {
    "id": "did:example:abcdef",
    "name": "Alice Example",
    "age": 23
  }
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Context}

The \texttt{@context} property defines the vocabulary used to interpret the 
credential.  
It specifies the VC data model version (typically W3C VC~2.0) and any additional
namespaces supporting the claims contained in the credential.

\begin{verbatim}
{
  "@context": [
    "https://www.w3.org/ns/credentials/v2"
  ]
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Identifiers}

The \texttt{id} is the unique identifier of the credential.  
It is a stable URI assigned by the issuer and allows a verifier to reference the
credential—e.g., when checking revocation information.

\begin{verbatim}
{
  "id": "https://example.org/credentials/235"
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Type}

The \texttt{type} array describes the category of the credential.  
It must always include \texttt{"VerifiableCredential"}, followed by one or more
application-specific types (e.g.\ \texttt{"DegreeCredential"}).

\begin{verbatim}
{
  "type": [
    "VerifiableCredential",
    "DegreeCredential"
  ]
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Issuer}

The \texttt{issuer} identifies the entity that created and signed the credential.  
It may be:
\begin{itemize}
    \item a URL controlled by the issuer, or  
    \item a DID, allowing retrieval of the issuer’s DID Document and public key.
\end{itemize}

\begin{verbatim}
{
  "issuer": "did:example:issuer1234"
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Name and Description}

These optional properties provide human readable information about the issuer,
such as name and a short description.  
They are rarely needed but may clarify credential provenance.

\begin{verbatim}
{
  "issuer": {
    "id": "did:example:issuer1234",
    "name": "Politecnico di Torino",
    "description": "Engineering University"
  }
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Validity Period}

The \texttt{validFrom} and \texttt{validUntil} fields define the time interval
during which the credential is valid.  
Credentials may expire (e.g.\ tickets, access tokens), and expiration is distinct
from revocation.

\begin{verbatim}
{
  "validFrom": "2025-10-18T11:12:23Z",
  "validUntil": "2026-10-18T11:12:23Z"
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Credential Subject}

The \texttt{credentialSubject} contains the claims about the subject, usually 
identified by a DID.  
Its structure must follow a schema published by the issuer on a verifiable data
registry, allowing verifiers to correctly interpret the semantics of the claims.

\begin{verbatim}
{
  "credentialSubject": {
    "id": "did:example:subject789",
    "degree": {
      "type": "BachelorDegree",
      "name": "BSc Computer Engineering"
    }
  }
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Status}

The \texttt{credentialStatus} field indicates how a verifier can check whether the
credential has been revoked or suspended.  
VC~2.0 commonly uses a \textbf{Bitstring Status List}, where each credential is
assigned a bit index:
\begin{itemize}
    \item 0 → credential is valid  
    \item 1 → credential is revoked or suspended  
\end{itemize}

\noindent
This mechanism is efficient, compressible, and suitable when most credentials
remain valid.

\begin{verbatim}
{
  "credentialStatus": {
    "id": "https://issuer.example.org/status/1",
    "type": "BitstringStatusListEntry",
    "statusPurpose": "revocation",
    "statusListIndex": "235",
    "statusListCredential": "https://issuer.example.org/status/1"
  }
}
\end{verbatim}

\medskip

\subsubsection*{Basic Components: Proof}

The \texttt{proof} section contains the issuer’s cryptographic signature.  
It guarantees the authenticity and integrity of the credential and includes:
\begin{itemize}
    \item the proof type (e.g.\ Data Integrity Proof),
    \item the cryptographic suite used,
    \item the creation time,
    \item the verification method (reference to the issuer’s public key),
    \item the actual proof value.
\end{itemize}

\begin{verbatim}
{
  "proof": {
    "type": "DataIntegrityProof",
    "cryptosuite": "eddsa-jcs-2022",
    "created": "2025-10-18T11:12:23Z",
    "verificationMethod": "did:example:issuer1234#key-1",
    "proofPurpose": "assertionMethod",
    "proofValue": "z3W5e8..."
  }
}
\end{verbatim}

\subsubsection {Advanced Proof Structures}

Beyond the basic single-signature model, the VC 2.0 specification supports more advanced proof mechanisms that allow multiple entities to sign the same credential or to sign it in a defined order.\\
These structures extend the expressiveness of the \texttt{proof} property and support more complex trust and attestation workflows.

\paragraph{Proof Set.}
A \emph{proof set} is an array of independent proofs, each created by a different entity.  \\
It is useful when the same credential must be signed by multiple issuers or authorities.  \\
The order of the proofs does not matter: each proof independently attests the integrity and authenticity of the credential.

\begin{verbatim}
"proof": [
  {
    "type": "DataIntegrityProof",
    "verificationMethod": "did:example:issuer1#key-1",
    "proofPurpose": "assertionMethod",
    "created": "2025-10-18T12:00:00Z",
    "proofValue": "zProofValue1"
  },
  {
    "type": "DataIntegrityProof",
    "verificationMethod": "did:example:issuer2#key-3",
    "proofPurpose": "assertionMethod",
    "created": "2025-10-18T12:05:00Z",
    "proofValue": "zProofValue2"
  }
]
\end{verbatim}

\paragraph{Proof Chain.}
A \emph{proof chain} is a sequence of proofs where each proof references the previous one. \\
This structure preserves the temporal order of signatures, which is important when the order of attestation matters—e.g., hierarchical approval workflows.
\medskip

\noindent
Each proof includes a \texttt{previousProof} field referring to the identifier of
the proof it builds upon.

\begin{verbatim}
"proof": [
  {
    "id": "urn:uuid:proof-1",
    "type": "DataIntegrityProof",
    "verificationMethod": "did:example:issuer1#key-1",
    "created": "2025-10-18T12:00:00Z",
    "proofValue": "zInitialProof"
  },
  {
    "type": "DataIntegrityProof",
    "verificationMethod": "did:example:issuer2#key-4",
    "created": "2025-10-18T12:10:00Z",
    "previousProof": "urn:uuid:proof-1",
    "proofValue": "zFollowUpProof"
  }
]
\end{verbatim}

\paragraph{Extended Proof Fields.}
VC proofs may contain additional properties beyond the minimal ones:
\begin{itemize}
    \item \textbf{id:} optional identifier for referencing the proof (useful in chains).
    \item \textbf{expires:} expiry time of the proof itself.
    \item \textbf{challenge:} — value provided by the verifier to prevent replay attacks.
    \item \textbf{nonce:} — holder-generated randomness, often used for privacy.
    \item \textbf{previousProof:} — reference to the earlier proof in a proof chain.
\end{itemize}

\begin{verbatim}
"proof": {
  "type": "DataIntegrityProof",
  "cryptosuite": "eddsa-jcs-2022",
  "created": "2025-10-18T12:30:00Z",
  "expires": "2025-10-18T12:45:00Z",
  "challenge": "zRandomVerifierChallenge",
  "nonce": "zHolderGeneratedNonce",
  "verificationMethod": "did:example:issuer123#key-1",
  "proofPurpose": "assertionMethod",
  "proofValue": "zSignatureValue"
}
\end{verbatim}

\paragraph{Use and Semantics.}
Multiple proof models enable:
\begin{itemize}
    \item multi-party attestation (multiple issuers),
    \item ordered approval flows (sign-after-sign),
    \item stronger integrity protection (each chain proof covers previous ones),
    \item replay-attack protection via challenges and nonces.
\end{itemize}


\noindent
Although DIDs are not exchanged directly between holder and verifier, every VC contains the holder’s DID inside \texttt{credentialSubject.id}, allowing the verifier to retrieve the correct public key from the holder’s DID Document.  \\
This ensures that proofs and verifiable presentations can be validated in a p2p SSI model.

\subsubsection {Trust Model}

The trust model behind the three-party interaction relies on the properties of verifiable credentials and verifiable presentations.\\  
The issuer creates and signs the verifiable credential, ensuring that the
credential is authentic and has not been tampered with during transmission or storage. \\
Holders and verifiers operate under the assumption that the credential received from the issuer is correct, provided that all cryptographic checks pass.
\medskip

\noindent
All entities in the ecosystem expect the VDR to be \textit{tamper-evident}. \\
Even if the VDR does not guarantee immutability, any modification to identifiers, schemas, or status lists must be detectable.
\medskip

\noindent
Furthermore, holders and verifiers expect the issuer to stand behind the claims included in the credential and to revoke the credential promptly when needed, allowing verifiers to check the status during authentication.

\subsubsection*{Implicit Trust and Root of Trust}

Implicit trust means that a holder or verifier trusts the issuer’s claims because of a pre-existing trust relationship. \\
This relationship is not mandated by the specification: implementations are free to decide how and why an issuer is trusted.
\medskip

\noindent
From an implementation point of view, implicit trust requires knowing the
issuer’s well-known DID.\\
This DID becomes the \textbf{root of trust} for verifying the credential, since it allows the verifier to retrieve the issuer’s DID Document and the associated public keys used to sign the credential.
\medskip

\noindent
Secure storage of these trusted DID is essential for both holders and verifiers.

\subsubsection*{Selecting Which Issuers to Trust}

The specification does not define a universal mechanism for determining which
issuers should be trusted.  
Different ecosystems adopt different strategies, including:

\begin{itemize}
    \item \textbf{Well-known organizations}, such as universities or government agencies,
    whose reputation provides a natural basis for trust.
    \item \textbf{Community-based trust}, where members of a closed ecosystem trust each
    other due to established membership rules.
    \item \textbf{Trusted service providers}, which maintain trusted lists or rank issuers.
    \item \textbf{Social trust}, where individuals rely on recommendations—similar to how
    users trust services because their peers do.
\end{itemize}

\noindent
Multiple strategies can coexist, and real deployments often combine them.

\medskip

\subsubsection*{Extensibility of the Data Model}

The VC data model supports \textbf{permissionless innovation}.  
Issuers may extend the model in two main ways:

\paragraph{Extending Vocabularies.}
Issuers can introduce new terms for describing attributes of the credential
subject.  
To do so, they define a new JSON-LD context that contains the vocabulary
extensions and make it publicly accessible.

\begin{verbatim}
{
  "@context": [
    "https://www.w3.org/ns/credentials/v2",
    "https://example.org/credentials/mycontext.json"
  ],
  "credentialSubject": {
    "id": "did:example:123",
    "newTerm": "Custom value"
  }
}
\end{verbatim}

\noindent
This mechanism ensures that verifiers can interpret the meaning of new
properties by consulting the corresponding context.

\paragraph{Extending Cryptographic Suites.} 
The specification allows the use of multiple cryptographic suites. \\
Implementations may choose traditional algorithms (e.g., EdDSA, ECDSA) or
post-quantum algorithms when needed.\\
If a new cryptosuite is designed, implementers can propose it to W3C for
standardization.
\medskip

\noindent
This flexibility ensures that verifiable credentials remain adaptable to future security requirements and evolving ecosystem needs.


\subsubsection*{Authorization (Out of Scope)}

After authentication the claims inside the \texttt{credentialSubject} are typically employed for authorization. \\
The VC specification does not define authorization rules; applications may adopt role-based or attribute-based access control depending on their requirements.

\subsection {Verifiable Presentations (VP)}
A \textbf{Verifiable Presentation (VP)} is a data structure created and signed by
a holder to present one or more Verifiable Credentials (VCs) to a verifier.
A VP may include:
\begin{itemize}
    \item one or multiple VCs,
    \item additional optional data,
    \item a short-lived proof, bound to a challenge provided by the verifier.
\end{itemize}
VPs are typically generated ``on the fly'' during an authentication process,
ensuring freshness and preventing replay attacks.

    \centering
    \includegraphics[width=\linewidth]{./images/section_5/vp_structure.png}
    \caption{Structure of a Verifiable Presentation.}
\end{figure}

\subsubsection*{Basic Components: Type}

The \texttt{type} property of a VP always contains the value
\texttt{"VerifiablePresentation"}.  
Additional presentation-specific types may be included depending on the
application context.

\begin{verbatim}
{
  "@context": ["https://www.w3.org/ns/credentials/v2"],
  "type": ["VerifiablePresentation", "ThisPresentation"]
}
\end{verbatim}

\subsubsection*{Basic Components: Holder}

The \texttt{holder} property identifies the entity creating and signing the
presentation.  
It is usually expressed as a DID:

\begin{verbatim}
"holder": "did:method:method_specific_id_holder"
\end{verbatim}

In self-asserted presentations, the holder may also issue the enclosed VC.

\subsubsection*{Basic Components: Verifiable Credential}

A VP must embed the \emph{entire} VC being presented.  
Extracting or copying partial data would break the cryptographic proof of the
original credential.

\begin{verbatim}
"verifiableCredential": [
  { ... VC ... }
]
\end{verbatim}

\subsubsection*{Basic Components: Proof}

The proof of a VP is similar to the proof of a VC but is created by the \emph{holder}
instead of the issuer. \\
It ensures that the presentation is fresh and legitimately produced by the entity
controlling the holder's private key.\\
A VP proof includes:
\begin{itemize}
    \item the proof type (e.g.\ Data Integrity Proof),
    \item the cryptographic suite used,
    \item the creation timestamp,
    \item the verification method (a reference to the holder’s public key),
    \item the proof purpose,
    \item the actual proof value.
\end{itemize}

\begin{verbatim}
"proof": {
  "type": "DataIntegrityProof",
  "cryptosuite": " ... ",
  "created": "2025-10-18T11:12:23Z",
  "verificationMethod": "did:method:holder_key",
  "proofPurpose": "authentication",
  "proofValue": " ... "
}
\end{verbatim}

\noindent
VPs are typically short-lived.\\
A verifier sends a nonce (challenge) to the holder, which must be included in the proof. \\
This prevents replay attacks and ensures that each presentation is fresh.

\subsubsection*{Self-Asserted Presentations}

A holder may generate a VP containing a \emph{self-asserted} VC—i.e.\ a credential not
signed by an issuer.  
Although less trustworthy, this is valid in scenarios where the verifier only
needs information provided directly by the holder.

\subsubsection*{Enveloped Verifiable Credentials}

A VP may embed a VC in a compact JOSE/JWT representation, referred to as an
\textit{Enveloped Verifiable Credential}.  
This is useful in systems adopting JOSE-based security layers (e.g.\ JSON Web Token,
JSON Web Encryption).

\begin{verbatim}
{
  "type": ["VerifiablePresentation", "DegreePresentation"],
  "verifiableCredential": [{
     "@context": ["https://www.w3.org/ns/credentials/v2"],
     "id": "data:application/vc+jwt,...",
     "type": "EnvelopedVerifiableCredential"
  }]
}
\end{verbatim}





\subsubsection{VC security Considerations}

The W3C Verifiable Credential ecosystem leaves implementers significant
freedom.\\
This flexibility is powerful, but it also introduces potential risks.\\  
The specification therefore includes several security considerations that
developers must evaluate carefully when designing issuers, holders and verifiers.

\vspace{0.4cm}
\subsubsection*{Cryptographic Suites and Libraries}

Implementations rely on cryptographic suites (EdDSA, ECDSA, BBS, ML-DSA,
etc.) and on third-party libraries. \\ 
Developers must:
\begin{itemize}
    \item understand the security properties and limitations of the selected suite,
    \item regularly monitor vulnerabilities and apply updates,
    \item evaluate the impact of cryptographic failures on already-issued VCs.
\end{itemize}

\noindent
If a cryptographic weakness is discovered, issuers may need to \textbf{revoke} or
\textbf{reissue} credentials.  
This highlights the essential role of a robust revocation mechanism.

\vspace{0.4cm}
\subsubsection*{Key Management}

The security of the entire SSI ecosystem depends on correct key management.  
Issuers and holders must:
\begin{itemize}
    \item generate keys using secure and standards-compliant methods,
    \item rotate signing keys periodically,
    \item store private keys securely (preferably in hardware),
    \item protect keys from extraction or misuse.
\end{itemize}

Weak key management compromises all signatures, and therefore the integrity of
VCs, VPs and DID Documents.

\vspace{0.4cm}
\subsubsection*{Content Integrity of External Resources}

A credential may reference external resources (such as URLs).\\
Since these resources may change, implementers must ensure integrity by:
\begin{itemize}
    \item hashing external resources and including the hash in the VC,
    \item using \texttt{relatedResource} or similar mechanisms,
    \item protecting referenced resources against unauthorized modifications.
\end{itemize}

\noindent
Otherwise, a verifier may validate the signature but rely on altered or malicious external data.

\vspace{0.4cm}
\subsubsection*{Unsigned Claims}

Self-asserted VCs or bearer-style credentials are allowed by the data model.
However:
\begin{itemize}
    \item only issuer-signed credentials are \textbf{verifiable},
    \item verifiers must interpret unsigned claims cautiously,
    \item authorization decisions should never rely solely on self-asserted data.
\end{itemize}

\noindent
The freedom to create arbitrary credential types must be balanced with security and authorization requirements.

\vspace{0.4cm}
\subsubsection*{Man-in-the-Middle, Replay, and Cloning Attacks}

SSI operates at the application layer, so secure communication channels are mandatory. \\
Interactions among holder, issuer and verifier must occur over:
\begin{itemize}
    \item TLS~1.3 secure channels (for confidentiality and authenticity)
    \item authenticated endpoints
    \item short-lived VPs bound to a challenge
\end{itemize}

\noindent
Replay attacks are mitigated using:
\begin{itemize}
    \item a \textbf{challenge} (nonce) provided by the verifier
    \item a validity period inside the VP proof
\end{itemize}

\noindent
Cloning is mitigated by securely storing VCs in the wallet and avoiding storage of previously generated presentations.

\vspace{0.4cm}
\subsubsection*{Bundling Dependent Claims}

Holders may combine multiple VCs inside a single VP.  
Issuers must therefore prevent “semantic recombination attacks”.

\noindent
Example:  
A university issues:
\begin{itemize}
    \item a VC stating the subject is a staff member in \textit{Computing},
    \item a VC stating the subject is a postgraduate student in \textit{Cyber}.
\end{itemize}

\noindent
A malicious holder could combine them to claim “staff in Economics”.\\
Mitigation:
\begin{itemize}
    \item encode roles in a single VC,
    \item ensure claim combinations cannot alter semantics or authorization.
\end{itemize}

\vspace{0.4cm}
\subsubsection*{Highly Dynamic Information}

Some claims change frequently (e.g.\ temporary roles, subscription status). \\
For such claims:
\begin{itemize}
    \item the issuer must set short validity periods,
    \item the verifier must check expiration and revocation,
    \item long-lived credentials should be avoided.
\end{itemize}

\noindent
Static properties (e.g.\ academic degrees) can instead be long-lived.

\vspace{0.4cm}
\subsubsection*{Device Theft and Impersonation}

Wallets must enforce strong local authentication:
\begin{itemize}
    \item biometrics,
    \item PINs or passphrases,
    \item hardware-backed secure storage.
\end{itemize}

If a device is compromised and VCs are not protected, attackers may impersonate
the legitimate holder.

\vspace{0.4cm}
\subsubsection*{Acceptable Use}

Issuers may specify a \texttt{termsOfUse} property to constrain how a credential may
be used.  
Verifiers must check:
\begin{itemize}
    \item whether the VC is used for its intended purpose,
    \item whether terms of use restrict its validity in the current context.
\end{itemize}

Ignoring these constraints may cause authorization errors or misuse.

\vspace{0.4cm}
\subsubsection*{Code Injection}

Credential Subjects must never contain executable code or scripts.  
All claims must be treated as untrusted input:
\begin{itemize}
    \item only JSON data should be allowed
    \item no HTML, JavaScript or scripting languages
\end{itemize}

\noindent
Improper sanitization can lead to code execution, HTML injection or storage attacks.
\vspace{2 cm}
\subsubsection{VC Privacy Considerations}

\noindent
Privacy considerations are a fundamental dimension of the SSI and Verifiable Credential framework.
\medskip

\noindent
Different types of information offer different degrees of privacy:

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.9\textwidth]{./images/section_5/privacy_consideration.png}
    \caption{Privacy spectrum: from highly correlatable identifiers to non-correlatable pseudonymous attributes.}
\end{figure}


\begin{itemize}
    \item \textbf{Highly correlatable identifiers (global IDs)}  government IDs, card numbers, shipping addresses. \\
    These enable long-term behavioral tracking and provide the least privacy.

    \item \textbf{Correlatable via collusion (PII)} such as name, birthdate, zipcode.  \\
    These can be linked by multiple verifiers or by collusion between verifier and issuer.

    \item \textbf{Non-correlatable attributes (pseudonyms)}  e.g., ``is over 21''.  \\
    These reveal only what is strictly needed and avoid unnecessary profiling.
\end{itemize}

\subsubsection *{User Privacy and Trust in Agents}

\noindent
The privacy guarantees of the VC ecosystem depend heavily on the behavior of the software agents involved:

\begin{itemize}
    \item \textbf{Issuers} must verify identity accurately but should avoid storing unnecessary
    personal information once the credential is issued.
    \item \textbf{Verifiers} are expected to validate VCs correctly and not retain identity data
    unless strictly necessary.
    \item \textbf{Wallets} must protect credentials at rest and ensure that only the information
    explicitly selected by the user is disclosed.
\end{itemize}

\noindent
SSI is built on the expectation that agents operate in the user’s best interest: the holder retains control over what to share, when, and with whom.

\subsubsection *{Data Minimization and Selective Disclosure}

Data minimization is the core privacy-preserving principle of SSI:
the issuer should embed only the attributes required for the intended purpose.
\medskip

\noindent
When multiple properties must coexist in a single credential, modern VC formats enable \textbf{selective disclosure}:\\
the holder can choose which attributes to reveal and which to hide, avoiding unnecessary correlation while still satisfying verifier requirements.

\begin{quotation}
  \textit{This particular aspect was underlined by the Vesco, since in his point of view, it is a most important feature to understanding about VC privacy}
\end{quotation}

\subsubsection *{Personally Identifiable Information}

Whenever possible, PII should be avoided in the \texttt{credentialSubject}.\\
Instead of disclosing a full birthdate, an ``age-over-18'' claim is preferable.
\medskip

\noindent
Sensitive data must be protected:

\begin{itemize}
    \item \textbf{in transit} using secure channels (TLS~1.3),
    \item \textbf{at rest} using secure storage in wallets or hardware-backed key stores.
\end{itemize}

\subsubsection *{Correlation Surfaces}

Correlation can arise from multiple sources:

\begin{itemize}
    \item \textbf{Identifiers} credential IDs, DIDs, pairwise vs.\ static identifiers.
    \item \textbf{Metadata} timestamps used with high granularity may reveal usage patterns.
    \item \textbf{Signatures} reused signatures allow linking of multiple presentations.
\end{itemize}

\noindent
Using new nonces and proof regeneration reduces correlation risk.

\subsubsection *{Device Tracking and Fingerprinting}

Even when VC data is minimal, other layers of the technology stack can leak identity:

\begin{itemize}
    \item IP address and network-layer identifiers,
    \item GPS/Galileo location data,
    \item browser/device fingerprinting.
\end{itemize}

\noindent
Privacy must therefore be considered holistically, not just within the VC layer

\subsubsection *{Issuer and Verifier Behavior}

The specification emphasizes:

\begin{itemize}
    \item Issuers must not store unnecessary personal data.
    \item Verifiers must request only the information strictly required.
    \item Wallets must prevent disclosure to unintended parties.
\end{itemize}

\noindent
This reduces liability and prevents data mining or replay by malicious entities.

\subsubsection *{Bearer Credentials}

Bearer credentials (``credenziali al portatore'') may be used in low-risk cases, but:

\begin{itemize}
    \item they are not verifiable,
    \item they lack binding to a DID,
    \item they reduce the verifier’s ability to authenticate the subject.
\end{itemize}

\noindent
They should not be used for sensitive or security-critical applications.

\subsubsection *{Correlation during Validation}

Third-party services used during verification may observe validation patterns and thus deanonymize users if not designed correctly

\subsubsection *{Storage Provider and Data Mining Risks}

Cloud-based wallets or backup services may create large honeypots of personal data.\\
Local storage with secure hardware support is generally preferable.

\subsubsection *{Credential Aggregation}

Combining multiple VCs in the same presentation may unintentionally reveal more information than each VC independently. Issuers should design credentials to minimize this risk and avoid roles or attributes that can be recombined in misleading ways.

\subsubsection *{Patterns of Use and Frequency of Issuance}

Repeated presentation of the same credential also enables tracking.\\
For privacy-critical scenarios, the specification encourages:

\begin{itemize}
    \item \textbf{single-use credentials},
    \item or frequently refreshed proofs.
\end{itemize}

\noindent
The trade-off is higher issuer workload.

\subsubsection *{Issuer Cooperation and Signature Design}

Issuers should adopt cryptographic suites that avoid deterministic signatures, reducing correlation caused by identical proof values across presentations.

\subsubsection *{Legal Processes and Mis-Sharing}

Users must be informed of situations in which identity data may be disclosed to law enforcement.\\
Wallets must warn users before sharing information with an untrusted verifier


\subsection{ VC and VP Exchange Protocol}

\subsubsection *{Verifiable Credential (VC) Issuance Logical Steps}

Given a Holder willing to obtain a Verifiable Credential, the Issuer performs the following steps:

\begin{enumerate}
    \item \textbf{Collect identity information} from the subject  
    (e.g.\ DID and additional attributes required by the Issuer).
    
    \item \textbf{Verify the identity information} and derive the \emph{claims} that will
    be asserted in the credential subject.
    
    \item \textbf{Verify proof of possession} of the private key corresponding to the
    Holder's DID (challenge–response).
    
    \item \textbf{Generate the credential} and associate it with the Holder's DID.
    
    \item \textbf{Sign the credential}, producing a \emph{Verifiable Credential}.
    
    \item \textbf{Update status information}  
    (e.g.\ assign a position in the Status List Bitstring and mark it as valid).
    
    \item \textbf{Issue the VC to the Holder}.
\end{enumerate}

\noindent
Before these steps take place, the Issuer is expected to:
\begin{itemize}
    \item maintain its own DID, DID Document and keys on the chosen VDR;
    \item publish the \textbf{VC schema} on the VDR;
    \item maintain a \textbf{revocation mechanism} (e.g.\ status list).
\end{itemize}

\vspace{0.5cm}

\subsubsection *{Verifiable Presentation (VP) Verification Logical Steps}

Given a Holder presenting a Verifiable Presentation (VP), the Verifier executes:

\begin{enumerate}
    \item \textbf{Retrieve the Holder's DID} from the VP.
    
    \item \textbf{Resolve the Holder's DID} using the appropriate DID method to obtain the
    Holder’s DID Document and public key.
    
    \item \textbf{Verify the VP proof} using the Holder's public key.
    
    \item \textbf{Verify the challenge} embedded in the VP  
    (freshness check to prevent replay attacks).
    
    \item \textbf{Extract the embedded VC(s)} from the VP.
    
    \item \textbf{Retrieve the Issuer DID} from each VC.
    
    \item \textbf{Resolve the Issuer DID} and obtain the Issuer's verification method.
    
    \item \textbf{Verify the VC proof} using the Issuer’s public key.
    
    \item \textbf{Validate VC metadata} (validity period, issuance time, expiration, ecc...).
    
    \item \textbf{Check the status of the VC}  
    (e.g.\ using the Status List Bitstring to determine whether it has been revoked).
    
    \item \textbf{Extract the credentialSubject} and apply the authorization logic.
\end{enumerate}

\noindent
These logical flows involve \textbf{all layers} of the SSI framework: DID resolution, integrity verification, status checking, and finally authorization based on the claims contained in the credential subject.

\newpage
\noindent
Now we have the able to interact and exchange VC and VP among the three main actors of the SSI ecosystem: Issuer, Holder and Verifier.\\
We simple can use different standards and protocols to perform these interactions, such as:
\begin{itemize}
    \item \textbf{OpenID Connect (OIDC)}     
    \item \textbf{Credential Exchange Protocols} such as the W3C Credential Exchange Protocol, which defines a framework for exchanging verifiable credentials between issuers, holders, and verifiers. It outlines message formats, workflows, and security considerations for credential exchange.
\end{itemize}

\subsubsection {OpenID Connect (OIDC)}

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.85\linewidth]{./images/section_5/OIDC.png}
    \caption{OIDC specifications for VC Issuance and VP Presentation}
\end{figure}

\noindent
OIDC defines two main protocols that enable interoperability in
the exchange of Verifiable Credentials (VCs) and Verifiable resentations (VPs):
\begin{itemize}
    \item \textbf{OpenID for Verifiable Credential Issuance (OIDC4VCI)}, used by a Holder to request and obtain a VC from an Issuer.
    \item \textbf{OpenID for Verifiable Presentations (OIDC4VP)}, used by a Holder to present a VP to a Verifier.
\end{itemize}

\noindent
These specifications define a uniform API that supports \textbf{any VC format and any cryptographic suite}. No credential–specific customization is required.

\bigskip

\noindent
OIDC4VCI introduces a set of endpoints used during the interaction between Holder and Issuer:

\begin{itemize}
    \item \textbf{Credential Endpoint (mandatory)}  
    The endpoint where one or multiple VCs of the same format are issued.

    \item \textbf{Nonce Endpoint (optional)}  
    Provides a fresh nonce used in \textit{proof of possession} of the key material.  
    Even if the specification avoids the term “DID”, the meaning is the same:  
    a Holder must prove control of the private key behind its identifier before the Issuer binds the VC to that identifier.

    \item \textbf{Deferred Credential Endpoint (optional)}  
    Allows delayed delivery of a VC.  
    Useful when the Issuer needs extra time for verification or when facing a high issuance load.
\end{itemize}

\subsubsection *{Mechanisms}

The specification defines several mechanisms supporting the issuance flow:

\begin{itemize}
    \item \textbf{Credential Offer}  
    The Issuer advertises which VC types can be issued, allowing the wallet to start the flow.

    \item \textbf{Status Notification (optional)}  
    Allows the wallet to learn whether a VC has been revoked or is no longer valid.

    \item \textbf{Metadata Publication (optional)}  
    The Issuer may publish schemas and VC metadata, typically on a Verifiable Data Registry.
\end{itemize}

\subsubsection *{Issuance Flows}

OIDC4VCI supports multiple issuance patterns, depending on the use case:

\begin{itemize}
    \item \textbf{Authorization Code Flow}  
    The Issuer obtains end-user information through authentication and consent inside the issuance flow.

    \item \textbf{Pre-Authorized Code Flow}  
    User authorization happens out-of-band.  
    The Holder is already authorized when contacting the Credential Endpoint.

    \item \textbf{Wallet-Initiated or Issuer-Initiated}  
    The flow may start directly from the wallet, or from an Issuer invitation (e.g., email, QR code).

    \item \textbf{Same-Device Offer}  
    The credential offer is received on the same device where the wallet runs.

    \item \textbf{Cross-Device Offer}  
    The offer is received on a different device and then transferred to the wallet.

    \item \textbf{Immediate or Deferred Issuance}  
    Depending on whether the Deferred Credential Endpoint is used.
\end{itemize}

\subsubsection{Authorization Code Flow}

This section summarizes the Authorization Code Flow as presented during the lecture.  
The specification introduces a distinction between the \emph{End-User} and the \emph{Wallet}, 
which together constitute the Holder in the SSI trust model.

\begin{figure}[h!]
    \centering
    \includegraphics[width=1\linewidth]{./images/section_5/OIDC4VCI_Flow.png}
    \caption{OIDC4VCI Authorization Code Flow for VC Issuance}
\end{figure}

\paragraph{(1) Flow Initiation} ~

\noindent
\textbf{(1a) Wallet-initiated.}\\
The End-User selects the desired Credential in the Wallet, which initiates the issuance flow by contacting the Issuer.
\medskip

\noindent
\textbf{(1b) Issuer-initiated.}  
The Issuer generates a Verifiable Credential Offer (e.g.\ QR code, URI) and sends it to the Wallet.  
Upon receiving the offer, the Wallet begins the flow.

\paragraph{(2) Fetching Issuer Metadata} ~

\noindent
The Wallet retrieves the Issuer Metadata from the Credential Issuer URL.\\ 
This metadata specifies:
\begin{itemize}
    \item supported credential types and formats,
    \item the Authorization Endpoint,
    \item the Credential Endpoint.
\end{itemize}
\noindent
These are required to correctly initiate the issuance process.

\paragraph{(3) Authorization Request} ~

\noindent
The Wallet sends an Authorization Request to the Authorization Endpoint.\\ 
This step typically involves:
\begin{itemize}
    \item End-User authentication,
    \item explicit user consent.
\end{itemize}

\paragraph{(4) Authorization Response} ~

\noindent
The Authorization Server processes the request and returns an \emph{Authorization Code}.\\
This code is required to obtain an Access Token.

\paragraph{(5) Token Request} ~

\noindent
The Wallet sends a Token Request to the Token Endpoint, including the Authorization Code.\\
After validation, the endpoint returns an \emph{Access Token}.

\paragraph{(6) Credential Request and Issuance} ~

\noindent
Using the Access Token, the Wallet sends a Credential Request to the Credential Endpoint, including the proof(s) of possession of the private key associated with the Holder's DID.\\
The Issuer then returns:
\begin{itemize}
    \item the Verifiable Credential (immediate issuance), or
    \item a Transaction ID + time interval, requiring a Deferred Credential Request.
\end{itemize}
